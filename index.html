1.2

Préparer son Mac

L'outil drakbase ne tourne que sur macOS. Il vient, comme le paquet Swift et l'aide pour Tauri, du dépôt public DrakBase/client, par HTTPS : ni compte GitHub ni accès à demander. La liste comprend aussi un gestionnaire de mots de passe (KeePassXCUn gestionnaire de mots de passe libre, qui range tout dans un seul fichier chiffré. L'outil drakbase y écrit lui-même une copie des clés de chaque app.), où l'outil range une copie des clés de chaque app.

Installer l'outil

Une fois par Mac. La commande télécharge le code depuis le dépôt public, à l'étiquette de la version voulue (v0.6.0 au 24 novembre 2026), et place la commande drakbase dans ~/.cargo/bin/, le dossier des programmes installés par cargo dans votre dossier personnel.

cargo install --git https://github.com/DrakBase/client --tag v0.6.0 am-cli --locked

La dernière étiquette se lit avec git ls-remote --tags --refs https://github.com/DrakBase/client.git 'v*'.

Créer le certificat de signature (apps macOS)

Un certificat auto-signé suffit. Dans Trousseau d'accès (à ouvrir par Spotlight) : menu Trousseau d'accès › Assistant de certification › Créer un certificat…, avec un nom à vous, le type d'identité « Racine auto-signée » et le type de certificat « Signature de code ». Son nom exact se lit ensuite avec :

security find-identity -v -p codesigning

C'est ce nom, entre guillemets, que prennent --sign-id, codesign et le réglage de signature de Xcode. S'il n'apparaît pas, ouvrir le certificat dans Trousseau d'accès et choisir « Toujours approuver » pour la signature de code, sous « Se fier ». Toutes les versions d'une app sont signées par ce même certificat : en changer demande une version de transition, qui déclare le nouveau.

Suggestion

Avec Claude Code, la skill publique drakbase fait tout ce parcours avec vous : elle écrit le code d'intégration et lance les contrôles, et vous laisse les mots de passe et l'accord pour publier. Suggestion : l'installer avec claude plugin marketplace add DrakBase/skill puis claude plugin install drakbase@drakbase, et demander dans le dossier de l'app « Branche les mises à jour DrakBase dans cette app ».

1.3

Se connecter au serveur

L'outil parle au serveur avec une clé d'accès personnelle (jeton d'APIUne clé d'accès créée dans l'administration, qui permet à l'outil d'agir en votre nom sans votre mot de passe. Elle a ses propres droits et une date d'expiration, et commence par amk_.). Il la range dans le trousseau du Mac, jamais dans un fichier. À refaire sur chaque Mac, et quand le jeton expire : au bout de 365 jours par défaut.

  1. 1

    Créer le jeton dans l'administration

    Sur updates.drakbase.com/admin/account, rubrique « Jetons d'API », bouton « Nouveau jeton ». Cocher les droits du tableau ci-dessous. Le secret n'est montré qu'une fois : le copier tout de suite.

  2. 2

    Donner le jeton à l'outil (drakbase login)

    drakbase login --server https://updates.drakbase.com

    La commande demande le jeton. Pour le coller depuis le presse-papiers : pbpaste | drakbase login --server https://updates.drakbase.com --token-stdin.

  3. 3

    Vérifier la connexion (drakbase doctor)

    La commande affiche le compte connecté et les droits du jeton, sans rien modifier.

Droit à cocherCe qu'il permet
Envoyer des versions (releases:write)créer une version, y déposer ses fichiers, la modifier tant qu'elle reste un brouillon
Publier (releases:publish)rendre une version visible des apps, la retirer, la passer de bêta à stable
Modifier la fiche (listing:write)changer la description et les captures d'écran de la page publique de l'app

Un jeton peut être limité à une seule app. Pour brancher une app qui n'existe pas encore sur le serveur, il ne doit pas l'être. Dans tous les cas, il ne donne jamais plus de droits que le compte qui l'a créé.

Pour changer de serveur ou de compte, drakbase logout retire l'adresse et le jeton du trousseau, puis drakbase login enregistre les nouveaux. Le jeton retiré reste valable sur le serveur : le révoquer dans l'administration s'il ne doit plus servir.

1.4

Brancher l'app

Une seule commande ajoute une app à DrakBase. Elle se lance dans votre propre terminal, à la racine du projet, parce qu'elle demande des mots de passe.

  1. 1

    Choisir l'identifiant de l'app (slugL'identifiant court et définitif d'une app sur le serveur, en minuscules, par exemple kiosque. Il apparaît dans les adresses du serveur.)

    De 1 à 64 caractères parmi les minuscules, les chiffres et le tiret, tiré du nom de l'app. Il ne change plus jamais.

  2. 2

    Lancer la commande qui branche l'app (drakbase init)

    drakbase init <slug>

    Pour une app Tauri destinée au Mac, ajouter --sign-id "<nom du certificat>". L'outil enchaîne quatre tâches :

    • créer les deux clés de signature de l'app, la principale et celle de secours, si elle n'en a pas encore ;
    • en ranger une copie dans KeePassXC, relire cette copie, puis mettre le mot de passe de la clé principale dans le trousseau ;
    • écrire la configuration des mises à jour dans le projet, sans toucher au code ni remplacer une clé déjà présente ;
    • ouvrir dans le navigateur une page de l'administration, déjà remplie, qui crée l'app sur le serveur.

    Elle demande le mot de passe de la base KeePassXC, et le chemin de la base la première fois.

    Pour une app Swift, il faut un vrai fichier Info.plist. Un projet Xcode récent n'en a souvent pas, car Xcode le génère : créer alors un petit Info.plist (un dictionnaire vide suffit), le renseigner dans le réglage « Info.plist File » (INFOPLIST_FILE) de la cible, puis relancer drakbase init. Xcode le fusionne avec les clés qu'il génère. Si le projet en a plusieurs, préciser lequel avec --plist <fichier>.

  3. 3

    Faire valider l'app par un superadmin

    Cette page est réservée aux superadminsLe rôle qui peut tout faire dans l'administration, dont créer des apps. Un éditeur, lui, ne gère que les apps qui lui sont confiées.. Un éditeur leur envoie l'adresse affichée par le terminal, qui se termine par /admin/add-app#…. Le superadmin vérifie que la page montre le même identifiant de clé que le terminal, puis valide. L'outil attend 15 minutes au plus ; relancer drakbase init reprend là où il s'était arrêté.

    Le superadmin vérifie l'identifiant de clé, puis valide : le même clic crée l'app, active sa clé et vous ajoute à ses éditeurs.

  4. 4

    Écrire le code restant

    Le terminal finit par une liste « Reste à faire » : ce qu'il faut encore écrire dans l'app pour qu'elle cherche et installe ses mises à jour.

    Écrire le code de mise à jour : ce qu'il reste à écrire dans une app Swift ou Tauri.

  5. 5

    Contrôler jusqu'à ce que tout passe (drakbase doctor)

    La commande refait tous les contrôles sans rien modifier : ✓ bon, ! avertissement, ✗ problème. Pour une app Swift déjà construite, ajouter --bundle <chemin>/Nom.app : elle vérifie aussi sa signature.

  6. 6

    Installer la première version à la main

    Depuis la page publique ou l'app construite, dans le dossier Applications. Les mises à jour automatiques partent de cette version-là : une version d'avant l'intégration ne sait pas se mettre à jour.

    Lancée depuis le DMG ou le dossier Téléchargements, l'app tourne depuis une copie en lecture seule : elle ne peut pas se remplacer, et se dit indisponible. Sans notarisationLa vérification d'une app par Apple. Sans elle, macOS bloque le premier lancement d'une app téléchargée, jusqu'à ce que l'utilisateur l'autorise., macOS bloque son premier lancement : Réglages Système › Confidentialité et sécurité › « Ouvrir quand même ». La page publique l'explique aussi.

Mise en garde

Une clé de signature perdue coupe l'app de toute mise à jour : les utilisateurs d'une app Tauri devraient la réinstaller à la main depuis la page publique. La copie que l'outil range dans KeePassXC ne protège que si la base KeePassXC a elle aussi une copie hors du Mac. Suggestion : pour des clés créées avant que l'outil ne les sauvegarde lui-même, lancer drakbase backup <slug>, qui les range et vérifie la copie.

Suggestion

Une app Swift embarque aussi la clé de secours. Si seule sa clé principale est perdue, drakbase restore <slug> --backup-key réinstalle la clé de secours depuis KeePassXC. Suggestion : signer avec elle une version de transition (--key ~/.appsmarket/keys/<slug>.backup.key), préparée avec un superadmin, puis la retirer du Mac.

1.5

Écrire le code de mise à jour

Ce que l'outil a déjà écrit dans le projet, et ce qu'il reste à écrire, selon le type d'app.

Une app Swift

paquet DrakBase

Déjà écrit par drakbase init, dans l'Info.plist

  • adresse du serveur DrakBaseFeedURL
  • clés publiques DrakBasePublicKeys

4Reste à écrire

  • la dépendance au paquet, produit DrakBase, depuis https://github.com/DrakBase/client.git à partir de la 0.6.0 ;
  • une attente au tout début du programme, avant tout le reste, pour que la nouvelle version laisse l'ancienne se fermer (RelaunchGate.waitForPreviousInstance()) ;
  • l'objet qui cherche et installe les mises à jour, avec sa fenêtre (Updater et UpdatePrompt) ;
  • le menu « Rechercher les mises à jour… » et la section des réglages (UpdatesCommands, UpdateSettingsSection).

Conditions

macOS 14 ou plus. L'app ne doit pas être isolée par le système (sandboxLe bac à sable de macOS : une app qui l'active ne peut toucher qu'à ses propres fichiers, ce qui l'empêche de remplacer son propre programme.), et doit être signée avec votre certificat, jamais en ad hocUne signature de code faite sans certificat. Elle ne dit pas qui a signé, donc l'app ne peut pas vérifier que la version suivante vient du même auteur..

Une app Tauri 2

plugin officiel + @drakbase/tauri

Déjà écrit par drakbase init

  • configuration des mises à jour tauri.conf.json
  • permissions de la fenêtre capabilities/default.json
  • plugins Rust Cargo.toml
  • paquets JavaScript package.json

3Reste à écrire

  • lancer npm install, qui télécharge l'aide @drakbase/tauri depuis le dépôt public ;
  • déclarer les quatre plugins (mise à jour, relance, réglages, version du système) dans le code Rust de démarrage, src-tauri/src/lib.rs ;
  • l'interface : le crochet React useUpdater() de @drakbase/tauri/react, qui cherche au lancement puis une fois par jour, ou les fonctions checkForUpdate et installUpdate.

Conditions

Garder les versions exactes des plugins posées par l'outil, les mêmes côté Rust et côté JavaScript. Un fichier de plateforme (tauri.macos.conf.json…) qui masque un de ces réglages est signalé par l'outil : c'est là qu'il se corrige. Sous Windows, l'installeur s'installe pour l'utilisateur seul, sans demander de droits d'administrateur.

Le code d'une app Swift, pas à pas

  1. 1

    Ajouter le paquet

    Dans Xcode : File › Add Package Dependencies…, adresse https://github.com/DrakBase/client.git, à partir de la version 0.6.0, produit DrakBase. Pour un paquet SwiftPM, dans Package.swift :

    .package(url: "https://github.com/DrakBase/client.git", from: "0.6.0"),
// puis, dans les dépendances de la cible de l'app :
.product(name: "DrakBase", package: "client"),

    L'app n'importe qu'un module, DrakBase, sans aucune autre dépendance.

  2. 2

    Attendre l'ancienne version au lancement

    La version relancée par une mise à jour doit attendre que l'ancienne soit fermée, avant toute autre chose : ouverture d'une base, App.init. Retirer @main de la structure App, et le mettre dans un nouveau fichier, par exemple Main.swift (jamais main.swift, qui ne peut pas porter @main) :

    import DrakBase

@main
@MainActor
enum Main {
    static func main() {
        RelaunchGate.waitForPreviousInstance()
        MonApp.main()
    }
}

    Pour une app AppKit sans SwiftUI : appeler RelaunchGate.waitForPreviousInstance() en tête de main.swift, avant NSApplicationMain.

  3. 3

    Créer l'updater, son menu et ses réglages

    Un seul updater par app, créé après cette attente. UpdatePrompt est la fenêtre de mise à jour (notes, progression, « Installer et relancer », « Plus tard »), UpdatesCommands ajoute « Rechercher les mises à jour… » après « À propos », et UpdateSettingsSection regroupe tous les réglages, canal bêta compris :

    import DrakBase
import SwiftUI

struct MonApp: App {
    @State private var updater: Updater = {
        let updater = Updater()
        updater.presenter = UpdatePrompt(updater: updater)
        updater.start()
        return updater
    }()

    var body: some Scene {
        WindowGroup { ContentView() }
            .commands { UpdatesCommands(updater: updater) }
        Settings {
            Form { UpdateSettingsSection(updater: updater) }.formStyle(.grouped)
        }
    }
}

    Pour une mise en page à soi, chaque réglage existe aussi séparément : UpdateChannelPicker, CheckForUpdatesButton, AutomaticUpdateChecksToggle… L'updater se passe aux vues plus profondes par .environment(updater).

Le code d'une app Tauri, pas à pas

  1. 1

    Installer les paquets

    npm install

    La commande télécharge l'aide @drakbase/tauri depuis le dépôt public, par HTTPS, avec les plugins ajoutés par drakbase init.

  2. 2

    Déclarer les plugins côté Rust

    Dans src-tauri/src/lib.rs (ou main.rs), dans le Builder :

    tauri::Builder::default()
    .plugin(tauri_plugin_updater::Builder::new().build())
    .plugin(tauri_plugin_process::init())
    .plugin(tauri_plugin_store::Builder::new().build())
    .plugin(tauri_plugin_os::init())

    Si l'app utilise tauri-plugin-single-instance, il se déclare en premier.

  3. 3

    Brancher l'interface

    Avec React, le crochet useUpdater cherche les mises à jour et donne leur état :

    import { useUpdater } from "@drakbase/tauri/react";

function Updates() {
  const updater = useUpdater(); // cherche au lancement, puis une fois par jour
  const { phase, update, progress, error } = updater;

  return (
    <section>
      {update && (phase === "available" || phase === "error") && (
        <button onClick={() => void updater.install()}>
          Installer la version {update.version} et relancer
        </button>
      )}
      {phase === "downloading" && progress && (
        <progress max={progress.total ?? undefined} value={progress.downloaded} />
      )}
      {phase === "error" && <p>{error}</p>}
      <button onClick={() => void updater.check()}>Rechercher les mises à jour</button>
    </section>
  );
}

    Le crochet donne aussi les notes de version (update.notes, en Markdown), le canal (settings.channel, updater.setChannel) et le choix des statistiques. Sans React : checkForUpdate(), puis installUpdate(update), et describeUpdateError(error) pour un message d'erreur en français. L'aide suppose "moduleResolution": "bundler", comme Vite et les modèles de Tauri.

Les cas particuliers

Un travail en cours à enregistrer

updaterShouldRelaunch · beforeInstall

Juste avant la relance, l'app peut enregistrer son travail, ou refuser de se relancer à ce moment. En Swift, par un UpdaterDelegate assigné à updater.delegate et gardé par l'app, car l'updater n'en garde qu'une référence faible. En Tauri, par l'option beforeInstall, appelée une fois l'archive vérifiée ; sous Windows, l'installeur ferme l'app aussitôt après.

Une app de barre des menus

CheckForUpdatesMenuItem · RESTART_EXIT_CODE

En Swift, mettre CheckForUpdatesMenuItem(updater:) dans le menu du MenuBarExtra ; la fenêtre de mise à jour fonctionne aussi. En Tauri, une app qui empêche sa fermeture (api.prevent_exit()) doit laisser passer la relance, quand le code de sortie vaut tauri::RESTART_EXIT_CODE.

Les statistiques anonymes

allowsAnonymousStatistics: false

Actives par défaut : l'app envoie un identifiant d'installation anonyme, que l'utilisateur peut couper dans les réglages. Le dire dans l'app, à côté du réglage. En Swift, Updater(allowsAnonymousStatistics: false) pour n'en envoyer jamais ; en Tauri, setShareStatistics(false) les coupe et efface l'identifiant.

Les guides complets arrivent avec les bibliothèques, à la version installée. Pour Swift, clients/swift/DrakBase/README.md, dans la copie que garde SwiftPM : .build/checkouts/client/ pour un paquet, SourcePackages/checkouts/client/ dans les DerivedData d'un projet Xcode. Pour Tauri, node_modules/@drakbase/tauri/clients/tauri/README.md. Ils se lisent aussi dans le dépôt public, sur GitHub : github.com/DrakBase/client.

Mise en garde

Une app Tauri branchée avant la 0.5 reste sur l'ancienne aide : en 0.x, la plage ^0.4.0 ne reçoit jamais la 0.5, et npm update n'y change rien. Sans l'aide 0.5.1 ou plus et le plugin de version du système, un Mac resté sur un ancien macOS reçoit une version qu'il ne peut pas lancer. Suggestion : relancer drakbase init <slug>, qui monte la plage à la version de l'outil (^0.6.0) et ajoute le plugin, puis npm install, et déclarer le plugin côté Rust ; drakbase doctor le signale tant que ce n'est pas fait.

Mise en garde

Une app branchée avant la 0.6 prend le paquet ou l'aide dans un dépôt privé, par SSH : kcampion/drakbase-apps-market, ou DrakBase/apps-market. Ses mises à jour n'en dépendent pas, car le dépôt ne sert qu'à construire l'app ; mais la construire demande encore un accès à ce dépôt privé. Suggestion : la passer au dépôt public, ce que drakbase doctor signale à partir de la 0.6. Pour une app Swift, l'adresse et le nom du paquet changent ensemble, car SwiftPM tire ce nom de l'adresse : .package(url: "https://github.com/DrakBase/client.git", …) et package: "client" ; dans Xcode, retirer le paquet puis le rajouter. Pour une app Tauri, drakbase init <slug> passe l'aide au dépôt public, puis npm install.

1.6

Publier une version

Publier se fait en deux temps. L'outil envoie d'abord un brouillon, que le serveur ne propose à aucune app. La publication le rend visible, depuis l'administration ou en relançant la même commande avec --publish. Aucun mot de passe à taper : celui de la clé vient du trousseau.

Une app Swift

Monter d'abord le numéro de version (MARKETING_VERSION dans Xcode), puis construire en Release, pour les deux types de processeurs Mac à la fois, et signer le bundle complet avec votre certificat, en dernier :

xcodebuild -scheme MonApp -configuration Release -derivedDataPath build ARCHS="arm64 x86_64" ONLY_ACTIVE_ARCH=NO
ditto build/Build/Products/Release/MonApp.app dist/MonApp.app
codesign --force --sign "<nom du certificat>" --timestamp=none dist/MonApp.app
drakbase doctor monapp --bundle dist/MonApp.app

Un paquet SwiftPM se construit avec swift build -c release --arch arm64 --arch x86_64, puis un script assemble le .app. codesign -dv dist/MonApp.app doit montrer Authority=<nom du certificat>, jamais Signature=adhoc. Ensuite, l'envoi :

drakbase release dist/MonApp.app --app monapp --channel stable --notes notes.md
drakbase release dist/MonApp.app --app monapp --channel stable --notes notes.md --publish

La première ligne fabrique l'archive de mise à jour et l'image disque d'installation (DMG), les signe avec la clé de l'app et les envoie en brouillon. La seconde publie ce même brouillon sans rien renvoyer. Le numéro de version est lu dans l'app elle-même (CFBundleShortVersionString).

Une app Tauri

drakbase exec monapp -- npx tauri build --target universal-apple-darwin
drakbase publish --app monapp --version 1.2.0 --channel stable --notes notes.md <fichiers…>

La première ligne construit l'app avec la clé de signature, que l'outil prête à Tauri le temps de la commande. La seconde envoie les fichiers produits dans src-tauri/target/…/bundle/, chacun avec sa signature .sig à côté, sauf le DMG :

  • pour macOS, l'archive .app.tar.gz et le .dmg ;
  • pour Linux, l'AppImageUn format d'app Linux : un seul fichier, lancé sans installation. C'est la seule forme qu'une app Tauri sait remplacer elle-même sous Linux. ;
  • pour Windows, l'installeur -setup.exe.

L'outil ne tourne que sur Mac : les fichiers construits sous Linux ou Windows y reviennent pour être publiés.

Le numéro de version vient de tauri.conf.json, sous sa forme exacte (1.2.0, 1.3.0-beta.1) : c'est le même qu'il faut donner à --version, car la signature de l'archive porte la version construite, et l'app refuse un écart. Dans bundle.targets, une même liste convient aux trois systèmes : ["app", "dmg", "nsis", "appimage"]. Éviter MSI, qui s'installe pour toute la machine et demande l'accord d'un administrateur à chaque mise à jour.

Mise en garde

Le parcours Windows d'une app Tauri (installation, mise à jour, relance) n'a pas encore été essayé sur un vrai PC. Suggestion : le vérifier sur une machine Windows avant d'y annoncer l'app.

Essayer la première mise à jour

Avant d'annoncer l'app, vérifier qu'une mise à jour arrive vraiment, sur le canal bêta pour ne toucher personne d'autre.

  1. 1

    Installer une version de départ

    Une version équipée, par exemple 1.0.0, installée dans le dossier Applications et lancée une fois.

  2. 2

    Publier une version plus haute en bêta

    Monter le numéro à 1.0.1-beta.1, construire, puis envoyer avec --channel beta et --publish. Les apps réglées sur stable ne la voient pas.

  3. 3

    Passer l'app installée en bêta

    Dans ses réglages : la section des mises à jour en Swift, le choix du canal de votre interface en Tauri.

  4. 4

    Rechercher, installer, vérifier

    « Rechercher les mises à jour… » propose la 1.0.1-beta.1 avec ses notes. « Installer et relancer » ferme l'app, la remplace et la relance ; « À propos » montre le nouveau numéro. Ensuite, passer cette version en stable dans l'administration, ou la retirer.

Ce qui encadre une version

Les versions ne font que monter

1.2.0, puis 1.2.1 ou 1.3.0-beta.1

Les numéros suivent la convention SemVerLa numérotation majeure.mineure.correctif, par exemple 1.2.0. Un suffixe comme -beta.1 marque une pré-version, plus basse que la version finale du même numéro.. Chaque version doit être plus haute que la dernière de son canal : une pré-version face à la dernière bêta, une autre face à la dernière stable. Une version déjà envoyée ne se renvoie pas, et un défaut se corrige par une version plus haute.

Le canal bêta

--channel beta

Seules les apps réglées sur bêta reçoivent une pré-version ; elles voient aussi les versions stables, donc toujours la plus haute. Passer une bêta en stable se fait dans l'administration, sans rien reconstruire.

Le retrait d'une version

administration, page de la version

Une version retirée n'est plus proposée, et ses téléchargements répondent « disparu » (code 410). Les apps qui l'ont déjà installée la gardent.

La reprise d'un envoi

relancer la même commande

Une publication interrompue reprend où elle en était : le brouillon est retrouvé, et les fichiers identiques (même contenu, même signature) ne repartent pas. Un brouillon repris garde ses notes, sauf si --notes est redonné.

Les notes de version

--notes notes.md

En Markdown, dans la langue des utilisateurs, sur ce qui change pour eux. Elles s'affichent dans la fenêtre de mise à jour de l'app et sur sa page publique.

Signer ou vérifier un fichier à part

drakbase sign · drakbase verify

Un fichier construit ailleurs se signe avec drakbase sign, puis s'envoie avec drakbase publish. Pour contrôler une signature sans rien envoyer, drakbase verify détaille chaque contrôle.

Mise en garde

Une app macOS signée en ad hoc (codesign --sign -) ne reçoit jamais de mise à jour, et drakbase release refuse de l'envoyer. Suggestion : signer le bundle complet en dernier, toujours avec le même certificat : codesign --force --sign "<nom du certificat>" --timestamp=none dist/MonApp.app.

1.7

Remplir la fiche publique

À la première publication, la page publique de l'app est vide : elle attend une description et des captures d'écran. Le jeton doit porter le droit « Modifier la fiche ».

  1. 1

    Écrire la description

    Du texte brut, 4 000 caractères au plus, en quelques paragraphes courts, dans la langue des utilisateurs : ce que fait l'app, pour qui, ses points forts.

  2. 2

    Prendre les captures d'écran

    3 à 6 images PNG, de 320 à 8 192 pixels de côté et 8 Mio au plus chacune, avec une légende de 200 caractères au plus. Des données de démonstration, jamais de vraies données personnelles.

  3. 3

    Essayer, puis envoyer (drakbase listing)

    drakbase listing monapp --description fiche/description.txt \
  --screenshot "fiche/1-principale.png=La fenêtre principale" \
  --screenshot "fiche/2-reglages.png=Les réglages" --dry-run

    Avec --dry-run, rien ne part. Sans lui, la description est remplacée, et les captures du serveur deviennent exactement cette liste, dans cet ordre.

  4. 4

    Déposer l'icône et rendre l'app visible

    Dans l'administration seulement, onglet « Informations » de l'app : une image PNG carrée de 512 Kio au plus, et la case « Visible sur la page publique ».

1.8

Publier une stack Docker ou un exécutable Linux

Une stackIci, un groupe de conteneurs Docker qui forment ensemble une seule app, décrits par un fichier compose.yaml et mis à jour ensemble. se destine à une machine Linux : un Raspberry Pi, un petit serveur. DrakBase sert ses images comme un registre Docker en lecture seule. Sur la machine, un petit programme, l'agent drakbase-stack, l'installe puis la met à jour en ne téléchargeant que ce qui a changé.

  1. 1

    Préparer le dossier de la stack (stack/)

    À la racine du projet, trois éléments :

    • le fichier compose.yaml, dont les services à publier se construisent sur place ;
    • un fichier .env.example avec les réglages que la machine pourra changer, comme le port ;
    • un dossier files/ pour les fichiers montés en lecture seule.

    Les données vivent dans des volumes nommés, car le dossier de la stack change à chaque version. Laisser Compose nommer volumes et réseaux : un nom fixe, ou une clé avec _ (db_data), devient une permission à faire accepter par la machine ; écrire dbdata ou db-data. Dans .env.example, une ligne NOM=valeur par réglage, et aucun nom qui commence par COMPOSE_ ou DOCKER_.

  2. 2

    Brancher la stack (drakbase init)

    Comme pour une app : clés, puis page d'ajout dans l'administration. L'outil crée aussi stack/stack.json, qui dit quel service surveiller, si l'agent peut revenir seul à la version précédente après un échec, et pour quels processeurs construire (arm64 et amd64 par défaut).

  3. 3

    Contrôler la stack (drakbase doctor)

    Avec le slug : drakbase doctor <slug>. Il lit le compose comme le fera la publication, puis comme l'agent le fera sur la machine : seuls les champs d'une liste sont admis, et tout autre est refusé avec son chemin (la liste est dans docs/PROTOCOLE.md, section « Compose »). Il affiche aussi ce que la stack demandera à la machine : ports, dossiers de l'hôte, réseau, socket Docker.

  4. 4

    Publier la stack (drakbase release --stack)

    drakbase release --app monapp --stack --version 1.0.0 --channel stable --notes notes.md

    L'outil construit les images, recompresse leurs couches, envoie un brouillon, puis affiche la commande d'installation.

  5. 5

    Installer sur la machine

    curl -fsSL https://updates.drakbase.com/install/drakbase-stack.sh | sudo sh
sudo drakbase-stack install monapp --key <clé publique principale>
sudo drakbase-stack auto on

    La première ligne installe l'agent, la deuxième la stack (elle montre ses permissions et les fait accepter), la troisième active la vérification quotidienne. La machine doit avoir Docker Engine 24 et Docker Compose 2.29 au moins. Rien ne s'installe sans validation : dans l'app si elle le propose, sinon par sudo drakbase-stack update monapp. L'agent se lance toujours en root, avec sudo. Une version qui demande une permission nouvelle s'arrête jusqu'à sudo drakbase-stack update monapp --accept.

Un exécutable Linux (une app cli) se publie de la même façon. drakbase init <slug> --cli écrit le fichier drakbase.json, dont le programme lit les clés publiques à la compilation. Chaque version se signe ensuite avec drakbase sign et s'envoie avec drakbase publish. L'agent drakbase-stack est lui-même publié ainsi.

Mise en garde

La commande d'installation contient la clé publique de l'app : c'est elle qui permet à la machine de refuser une fausse version. Suggestion : la transmettre telle que drakbase release l'affiche, par un canal de confiance, sans la retoucher.

1.9

Quand quelque chose ne va pas

Une seule commande fait le point sans rien modifier, à lancer à la racine du projet (drakbase doctor). Sous chaque problème, elle donne presque toujours la correction. Les cas les plus fréquents :

Ce que dit l'outilCe qu'il faut faire
Le branchement reste sur « En attente de l'administration… » alors que la page dit l'app prêteLe compte du jeton n'est pas éditeur de l'app, donc il ne la voit pas : un superadmin l'ajoute dans l'onglet « Éditeurs » de l'app.
Le jeton est refusé : expiré, révoqué ou sans le bon droitCréer un nouveau jeton dans « Mon compte », puis relancer drakbase login.
Le mot de passe de la clé principale manque dans le trousseauLancer drakbase backup <slug>, qui le vérifie puis l'y range.
L'app est « signée ad hoc » ou « n'est pas signée »La signer avec le certificat, puis relancer l'envoi.
La version est déjà publiée, ou l'envoi répond « conflict »Monter le numéro de version : une version publiée ne change plus.
La version est déjà publiée en bêtaLa passer en stable dans l'administration, sans rien renvoyer.
La page publique ne montre pas l'appCocher « Visible sur la page publique » (onglet « Informations »), et publier une version stable.
L'outil est connecté au mauvais serveur, ou avec le jeton d'un autre comptedrakbase logout, puis drakbase login.
« @drakbase/tauri plus ancien que l'outil : la plage ^0.4.0… »Relancer drakbase init <slug>, puis npm install, et déclarer côté Rust le plugin ajouté.
La version du projet est une pré-version plus basse que la dernière stablePersonne ne la recevrait : prendre une pré-version de la version suivante.
Un champ du compose « n'est pas pris en charge dans une stack »Le retirer de compose.yaml ; la liste des champs admis est dans docs/PROTOCOLE.md, section « Compose ».
Sur la machine : « lecture de …/state.json : accès refusé »Relancer la commande de l'agent avec sudo.
Sur la machine : une permission nouvelle arrête la mise à jourLire la liste, puis lancer sudo drakbase-stack update <slug> --accept si on l'accepte.

La liste complète des messages est dans la skill Claude, fichier skills/drakbase/references/depannage.md du dépôt public DrakBase/skill.
